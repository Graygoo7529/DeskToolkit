# Windows 轻量系统 CLI：需求澄清与架构指南

> 暂定命令名：`workctl`，可以在实现前更换。本文是第一版设计说明，不是已完成的软件，也没有对新电脑执行操作。
>
> 核心定位：一个随手打开、先看状态、再执行明确操作的 Windows 命令行小工具。只围绕「自动登录配置」和「开发环境」展开，不重复已有的项目工作台。

## 1. 先确定什么做、什么不做

### 1.1 已确定的需求

- Windows 本地运行，优先支持 Windows 11 x64。
- Rust 实现，安装后直接运行一个命令，不依赖 Python 或 Node 运行时。
- 无参数进入交互菜单；明确的子命令用于快捷操作和脚本。
- 两种入口共用业务逻辑，不能出现「菜单能做、命令行做不了」或结果不一致。
- 默认先读状态，操作后重新读取并显示结果。
- 自动登录只读取、设置 `AutoAdminLogon`，不处理用户名和密码，不判断是否真的能够自动登录。
- 开发环境以实际工具、路径和配置的可见性为核心，不重新实现 fnm、uv、Conda、rustup 等版本管理器。
- 新增工具的检查器时，不需要改动整套交互和输出逻辑。

### 1.2 第一版的边界

| 功能 | 第一版 | 暂不做 |
|---|---|---|
| 自动登录 | 查看开关配置，明确设置开/关，写后验证 | 凭据配置、实际登录验证、自动重启、密码读取 |
| 开发环境 | 工具发现、版本与路径检查、配置诊断、按工具查看详情 | 一键安装所有工具、自动升级、自动搬迁环境 |
| 开发环境管理 | 输出具体的后续操作建议；可选显式 Rust 编译测试 | 自动修复 PATH、批量改环境变量、切换所有项目环境 |
| 应用本身 | 简单配置、JSON 输出、清晰错误 | 常驻服务、联网后台扫描、动态插件、复杂全屏 TUI |

不纳入：项目启动器、项目列表、存储清理、数据集与模型管理、备份、Windows 更新控制、通用「系统优化」。你已有的项目工作台继续负责项目级操作。

**开发环境第一版可以有明确价值，而不必立即写系统配置。** 能回答「装在哪里、当前实际调用谁、为何当前终端找不到、下一步该检查什么」，已经能避免大量重复排查。写入能力等检查流程稳定后按需加入。

## 2. 技术路线：保留 clap + dialoguer

建议采用：

| 依赖 | 职责 | 取舍 |
|---|---|---|
| `clap` | 参数解析、子命令、帮助信息 | 命令行接口的唯一入口定义 |
| `dialoguer` | 选择菜单、简单输入 | 足够覆盖本工具，不必上全屏 TUI |
| `console` | 少量颜色和文本样式 | 可选；也可先只使用纯文本 |
| `serde` / `serde_json` | 结构化结果和 JSON 输出 | 让脚本与测试不依赖中文文案 |
| `thiserror` | 有类型的业务错误 | 比到处拼接错误字符串更易维护 |
| `winreg` 或 `windows` | Windows 注册表、必要平台 API | 注册表需求简单时选前者；不要为同一接口重复引入两套封装 |
| `toml` | 用户配置 | 有明确配置需求后再加 |

第一版使用同步实现即可。不要为了几条本地探测命令引入异步运行时、数据库、依赖注入框架或插件协议。先处理好超时、取消和错误隔离，比并发检查更重要。

`dialoguer` 提供选择、输入等小型交互组件，符合这里的菜单式工作方式。只有以后真的需要持续刷新的进程列表、多窗格视图等，才值得考虑全屏 TUI。[dialoguer 文档](https://docs.rs/dialoguer/latest/dialoguer/)

应用项目提交 `Cargo.lock`；依赖版本在实现时选定并锁定，不在需求文档中追逐每个库的最新版本。

## 3. 使用方式与交互设计

### 3.1 首页保持短小

```text
workctl

自动登录配置   已开启 · AutoAdminLogon="1"
开发环境       尚未扫描

> 自动登录
  开发环境
  退出
```

首页只做很轻的状态读取。不要每次进入工具就启动 Conda、GitHub CLI 等所有探测，拖慢一个本来只想切换开关的操作。

进入开发环境页后再扫描，显示完成时间；用户可以刷新。返回首页时可以保留本次进程内的结果，但要标明它是上次检查，而不是实时状态。

### 3.2 自动登录页

```text
自动登录配置：已开启
AutoAdminLogon = "1"（REG_SZ）

> 关闭
  刷新
  返回
```

选择「关闭」就是明确操作，不再追加重复确认框；成功后显示：

```text
已关闭配置：AutoAdminLogon = "0"
```

这里显示的是配置状态，不使用「下次一定免登录」之类的文案，也不展示用户名、密码等无关信息。权限不足只说明「需要管理员权限」，并给出同一目标的命令；不自动提升整个菜单的权限。

### 3.3 开发环境页

```text
开发环境 · 本次检查

Node.js       可调用       fnm / node / npm
Python        部分可调用   uv 可调用；conda 未在当前进程 PATH 中发现
Rust          可调用       编译和链接尚未测试
Git / GitHub  可调用       未检查远端连接和登录状态

> 查看某项详情
  诊断配置
  刷新
  返回
```

以上只是界面示意，不代表当前电脑的实际检查结果。

工具详情按「状态 → 证据 → 原因 → 下一步」组织，避免无差别输出完整环境变量和长日志。

```text
工具：Conda
当前命令解析：未发现
配置的候选位置：D:\apps\miniforge3
候选安装：已发现（尚未执行）

说明：当前进程不可调用，不等于未安装。
建议：在 Miniforge Prompt 中检查，或显式检查上述候选安装。
```

用户取消选择返回上一级，`Ctrl+C` 结束程序。无交互终端时不启动菜单，应显示用法或要求明确子命令，不要等待一个永远不会出现的输入。

### 3.4 命令契约

```powershell
workctl                              # 交互入口
workctl autologon status              # 只读配置
workctl autologon set on              # 明确写入 REG_SZ "1"
workctl autologon set off             # 明确写入 REG_SZ "0"
workctl env status                   # 常规工具概览
workctl env status --tool rust       # 仅检查 Rust
workctl env doctor                   # 解释检测到的配置问题
workctl env doctor --tool python     # 缩小范围
workctl env test rust                # 可选：明确执行最小编译测试
workctl env status --json            # 稳定的机器可读结果
```

不要提供脚本用的 `toggle`：脚本重试一次就可能把设置反向改回去。菜单可以只显示当前状态的相反操作，但内部仍转换为明确的 `set on/off`。

建议统一退出码：`0` 请求成功；`1` 执行失败；`2` 参数错误；`3` 权限不足；`4` 验证失败或诊断发现需要处理的问题。`env status` 成功完成检查即返回 `0`，即使某个工具未安装；`env doctor` 的问题严重程度需要预先定义，未安装的可选工具不算失败。

JSON 的 stdout 只输出 JSON，进度与错误辅助信息走 stderr；包含 `schema_version`，状态使用稳定英文标识，中文仅用于展示。不要让外部脚本解析带颜色的表格。

## 4. 自动登录模块：小而准确

### 4.1 唯一操作对象

```text
Hive:  HKEY_LOCAL_MACHINE
Key:   SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon
Value: AutoAdminLogon
Type:  REG_SZ
Data:  "1" / "0"
```

微软文档说明该配置采用字符串值；完整自动登录流程还涉及其他条件，但那些条件不属于这个工具的职责。[微软自动登录说明](https://learn.microsoft.com/en-us/troubleshoot/windows-server/user-profiles-and-logon/turn-on-automatic-logon)

### 4.2 状态必须忠实于读取结果

| 读取结果 | 展示 | 操作行为 |
|---|---|---|
| `REG_SZ "1"` | 已开启 | 可设置关闭 |
| `REG_SZ "0"` | 已关闭 | 可设置开启 |
| 值不存在 | 未配置 | 显式设置时创建该值 |
| 其他字符串 | 非标准值 | 展示原值；显式 set 可归一为目标值 |
| 类型不是 REG_SZ | 类型异常 | 第一版拒绝覆盖，给出错误，不静默转换 |
| 权限不足 | 无法读取：权限不足 | 不当作关闭 |
| Winlogon 键不存在、其他 I/O 错误 | 无法读取 | 不新建整条系统键路径 |

为保持自用便捷，非标准字符串执行显式 `set` 时可以直接写成目标字符串；异常类型则交给用户排查，不增加隐含的修复行为。

### 4.3 写入流程

1. 仅打开目标键，申请必要访问权限；x64 版本使用明确的 64 位注册表视图。
2. 重新读取该值，而不是使用菜单打开时的旧状态。
3. 若已经等于目标值，返回「无需修改」。
4. 若需要修改，仅写 `AutoAdminLogon`，关闭时写 `"0"`，不删除值。
5. 立即重新读取，确认类型和目标值一致后报告成功。
6. 失败时保留具体原因，不报告已经完成，也不自动反复写入。

不读取、枚举、保存或导出 `DefaultPassword`、用户名、域名、LSA secrets。不要为了一个开关备份整个 Winlogon 键；日志至多记录此开关的前后状态。写后验证是即时校验，不承诺其他进程或系统之后不会再次修改它。

普通权限启动应用。第一版写入遇到权限不足时，让用户在管理员终端执行明确子命令即可；不要自动修改系统权限、注册表 ACL 或后台服务。也不要为了切换一个开关让所有开发工具检查都在管理员身份下运行。

## 5. 开发环境模块：围绕你正在用的工具

### 5.1 检查对象

| 工具组 | 检查重点 | 不应做的推断 |
|---|---|---|
| fnm / Node / npm | 命令来源、版本、Node 当前路径、多个候选入口 | fnm 安装了不等于当前终端完成初始化 |
| uv / Python | uv 版本，托管 Python 位置，缓存配置；解释全局与项目环境差别 | `python` 不在 PATH 不等于 uv 的 Python 不可用 |
| Miniforge / Conda | 命令是否可调用，base 路径、环境位置、包缓存与配置来源 | 普通 PowerShell 找不到 conda 不等于未安装 |
| rustup / rustc / Cargo | 工具链、host、Cargo/Rustup home、命令是否对应同一套安装 | `rustc --version` 成功不等于链接器和 SDK 完整 |
| Git / gh | 路径、版本、Git credential helper 的名称等非秘密配置 | `gh` 已安装不等于 Git 推送必然可用 |

WSL2、Docker、GPU 工具链留作未来的可选检查器。未配置这些检查器时，不在首页给出红色「缺失」。

### 5.2 你的路径可以作为初始配置，不是硬编码规则

依据此前你贴出的输出，可以预填以下候选信息；程序运行时仍需重新检测：

| 项目 | 路径 / 说明 |
|---|---|
| uv 托管 Python | `D:\apps\uv\python` |
| uv 缓存 | 计划使用 `D:\app_cache\uv`，检测实际生效值 |
| Miniforge | `D:\apps\miniforge3` |
| Conda 包缓存 | `D:\app_cache\conda\pkgs` |
| Rustup home | `D:\apps\rustup` |
| Cargo home | `D:\apps\cargo` |
| Cargo 可执行入口 | `D:\apps\cargo\bin` |
| Git | 此前输出来自 `C:\Program Files\Git` |

此前工具版本仅作为历史背景，不能作为软件中的「正确版本」。尤其 C++ Build Tools 和 Windows SDK 的安装完成状态，应重新检查，不能根据开始下载或 Rust 版本输出认定已就绪。

### 5.3 区分三种信息

1. **当前进程实际使用的信息**：本程序继承的 PATH、环境变量、实际解析到的命令。
2. **持久化配置**：用户级和系统级环境变量、工具自身的配置文件。
3. **候选安装位置**：用户在本工具配置中登记的位置，或受控发现得到的位置。

这三者可能不同。例如用户刚改了环境变量，旧终端启动的 `workctl` 仍继承旧值。输出应明确说「新终端可能生效」，不能把持久化值当作当前实际值。

本工具无法读出父 PowerShell 中没有导出的函数和内部状态，也不能凭普通子进程解析完全复现 shell alias/function 的优先级。因此「当前命令来源」应说明是本进程的外部命令解析结果，而非保证等同于父 shell 的所有行为。

### 5.4 从轻检查到深检查

- **status**：发现可执行入口、读取安全的版本信息，显示检查时间与来源。
- **doctor**：按工具继续检查指定的配置、多个安装来源、变量是否冲突；给出可执行的建议，不自动修改。
- **test rust**：用户明确选择后，在应用创建的独立临时目录生成最小、无第三方依赖的 Rust 程序并编译，验证编译与链接；不使用用户项目，不下载依赖，不自动安装工具。测试后清理自己创建的文件，失败可选择保留以排查。

MSVC 目标编译需要链接器及 Windows API 库，单纯打印编译器版本不够。[Rustup 的 MSVC 前置条件](https://rust-lang.github.io/rustup/installation/windows-msvc.html)

所有命令都设置合理超时和输出上限，某个检查失败不阻止其他检查。对网络、GitHub 登录、远程 Git 连接等检查，应单独提供显式操作，默认诊断不发起它们。

### 5.5 后续哪些管理操作值得做

第一版完成后，按真实需求逐项增加，而不是一口气实现：

- 对少量受支持的用户级配置提供「当前值 → 目标值 → 修改 → 重读」流程。
- 给已有工具的维护命令提供明确入口，但始终说明调用哪个工具、改哪个范围。
- 导出脱敏的诊断报告，便于与你的其他助手或开发工具共享。

第一批写入能力不建议是「迁移 Python/Rust 安装目录」或「整理 PATH」。改变 `CARGO_HOME`、`RUSTUP_HOME` 等变量并不会自动搬迁已有内容；必须设计独立迁移流程。Cargo home 还可能含配置与凭据，不能把整个目录视为缓存。[Cargo home 文档](https://doc.rust-lang.org/cargo/guide/cargo-home.html)

## 6. 架构：一个 crate，清楚的边界

```text
src/
  main.rs                 # 组装依赖、选择入口、退出码
  cli.rs                  # clap 参数定义
  interactive.rs          # 菜单和输入；不直接操作注册表
  app.rs                  # 用例入口：读取、设置、诊断
  model.rs                # 状态、诊断项、操作结果
  output.rs               # 文本 / JSON 渲染
  features/
    autologon.rs          # 单字段状态与写入规则
    dev_env/
      mod.rs              # 探测编排与注册
      node.rs
      python.rs
      rust.rs
      git.rs
  platform/
    mod.rs                # 平台接口
    windows.rs            # 注册表、用户/系统环境读取
    process.rs            # 外部命令执行、超时与输出限制
  config.rs               # 可选候选路径、启用的检查器
```

逻辑调用方向：

```text
CLI / 菜单
    ↓
应用用例
    ↓
功能规则与检查器
    ↓
注册表 / 命令执行 / 环境与文件访问
```

结果对象返回后，由展示层输出。检查器不要直接 `println!`、弹菜单或写日志；这样同一结果可以用于终端、JSON 和测试。

### 6.1 只抽象真正需要替换的地方

建议建立三个小接口：

- `AutologonStore`：读取目标值、写目标字符串。真实实现是 Windows 注册表，测试实现是内存对象。
- `CommandRunner`：接收明确程序路径、参数、工作目录、超时；返回退出状态、受限输出与是否超时。
- `EnvironmentReader`：读取当前进程、用户、机器作用域内允许检查的环境配置。

不要一开始把所有 feature 都塞进一个包含十几种方法的「万能插件 trait」。自动登录是可写系统设置，工具检查是诊断任务，两者共享结果展示和平台基础设施即可，不必强行拥有同一生命周期。

### 6.2 结果模型

建议至少区分：

```text
ToolReport
  id / display_name
  availability: callable | candidate_only | not_found | error
  version
  executable_path
  observed_at
  observations[]   # 证据及来源
  diagnostics[]    # 级别、稳定代码、说明、下一步

ApplyResult
  changed
  before
  after
  verified
```

缺失可选工具是 `info`，路径多套但当前明确可用可能是 `warning`，命令本身执行失败是 `error`。不要把所有非绿色状态都解释成必须修复。

### 6.3 新增检查器的方法

1. 定义它要回答的问题，以及哪些证据足够支持结论。
2. 实现一个检查器，返回统一结果，不输出 UI。
3. 在静态注册列表中加入 ID、名称与执行入口。
4. 为正常、缺失、超时和异常输出添加样例测试。
5. 菜单和 JSON 自动复用既有展示逻辑。

只有需要新类型的操作时才扩展应用用例，不通过配置文件执行任意脚本。

## 7. Windows 实现细节

### 7.1 外部命令执行

- 优先明确可执行文件路径和参数数组，避免拼接一段 shell 字符串。
- 使用受控工作目录，避免工具从随机项目目录加载项目专属配置或执行钩子。
- 识别 Windows 下 `.exe` 与 `.cmd` 的差异；npm 等可能通过脚本入口调用。需要命令解释器时，只使用内置固定模板和验证过的参数，不能把用户输入直接拼进去。
- 工具路径以候选事实记录，执行候选工具前区分其来源；不递归扫整块硬盘并运行所有同名文件。
- 超时后等待退出并回收资源；对于可能产生子进程的深检查，使用 Windows Job Object 等可靠方式管理进程树，不只杀掉父进程。
- 不用完整环境变量转储诊断。尤其不要输出令牌、密钥、密码、认证配置全文。

### 7.2 配置与权限

- 本应用配置使用用户级位置，路径可覆盖；不要求管理员安装应用本身。
- 配置只保存候选路径、启用的检查器、显示偏好，不保存工具凭据。
- 如后续支持修改环境变量，明确区分用户级与系统级，默认只做用户级；不要把当前进程 PATH 原样覆盖到持久化 PATH。
- 自动登录的写操作需要足够权限，但开发工具检测不应自动跟随提升权限。
- 本文只是软件设计，不代表已经授权任何助手修改实际系统设置。

## 8. 分阶段实施

### 阶段 A：最小可用骨架

- 建立 Rust 项目、clap 命令、菜单、纯文本/JSON 输出。
- 定义状态类型、错误和退出码。
- 用假的后端把全部界面跑通。

验收：无参数有菜单；非交互模式不等待输入；CLI 和菜单给出一致结果。

### 阶段 B：自动登录闭环

- 实现单字段注册表读取。
- 实现明确 set、幂等检查、写后读取和权限错误。
- 普通权限测试读取；真实写入只在用户选择的 Windows 测试环境中手动验收。

验收：只触碰 `AutoAdminLogon`，不读取凭据；开启/关闭/未配置/异常状态都能区分。

### 阶段 C：开发环境只读检查

- 先实现 Rust 和 uv 两组，验证探测模型。
- 再增加 fnm/Node、Conda、Git/gh。
- 添加命令来源、候选路径、配置来源和建议。

验收：工具缺失不会使整个扫描崩溃；未检测不能显示成已就绪；父进程环境与持久化配置不混淆。

### 阶段 D：稳定化与交付

- 超时、取消、输出限长、敏感信息排除。
- 可选 Rust 编译测试。
- Windows CI、发布包、使用说明。
- 实际使用一段时间后，再挑选一项有价值的环境管理写操作。

不需要把所有阶段拆成多个 crate 或做完整插件系统。优先交付少量可靠能力。

## 9. 测试与验收清单

| 场景 | 预期 |
|---|---|
| 开关已为目标值 | 不写入，返回无需修改 |
| 字段缺失 | status 显示未配置；显式 set 创建单个值 |
| 字段类型异常 | 明确错误，不误显示关闭，不静默覆盖 |
| 权限不足 | 不崩溃、不提权重试所有任务，返回可执行建议 |
| 写入后读回不一致 | 报验证失败，而不是成功 |
| 模拟 Winlogon 中存在密码字段 | 测试后端确认程序从未读取或枚举该字段 |
| PATH 没有 conda，候选安装存在 | 显示候选安装与当前不可调用两件事实 |
| 环境变量仅持久化修改 | 不冒充当前进程已经生效 |
| 一个命令超时或输出格式变化 | 单项报错，其余继续 |
| 带空格/中文的安装路径 | 参数传递正确，不产生 shell 拼接错误 |
| 输出 JSON | 可解析、无颜色、无菜单、字段结构稳定 |
| Rust 版本成功但链接失败 | 区分工具存在与构建能力失败 |
| 未安装 WSL/Docker | 若未启用相关检查，不算故障 |

单元测试使用内存注册表后端与固定命令输出。Windows 集成测试使用专门的测试键，不让 CI 修改真实 Winlogon。测试配置不能通过普通运行参数任意改变生产自动登录目标键。

## 10. 构建与交付

实现仓库应包含：

```text
README.md              # 安装、命令、管理员操作方式
ARCHITECTURE.md         # 模块边界与新增检查器流程
Cargo.toml
Cargo.lock
src/
tests/
.github/workflows/     # Windows 构建与测试
```

开发阶段：

```powershell
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --release --locked
```

首个发布目标为 `x86_64-pc-windows-msvc`。在 Windows 构建并实际测试菜单、注册表权限和命令解析，不用 Linux 上的单元测试代替 Windows 验收。

发布包可以是 ZIP：可执行文件、README、许可证、校验和。用户解压到例如 `D:\apps\workctl` 后直接运行；是否加入 PATH 由用户选择。没有必要先制作复杂安装器。

「单个 exe」不等于可以跳过运行库兼容性验证。按最终链接方式检查干净 Windows 环境的运行需求，并在 README 记录；不要未经验证承诺任意电脑零依赖运行。

## 11. 推荐结论

这份工具的第一版，最值得做好的是：

1. **一个极简而可靠的自动登录配置开关。**
2. **一个能解释当前开发环境状态的本地诊断面板。**

保留 `clap + dialoguer`。用一个 crate、两套入口、共享的应用用例，以及少量可测试的平台接口，把边界打清楚。自动登录不扩张成账号管理器，开发环境不扩张成万能安装器；后续每次只增加一个确实能省事的能力。
